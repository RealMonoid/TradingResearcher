# Certified reference compositions

This implements [research-contract/1.0 section 14.1](../docs/architecture/14_RETAIL_RESEARCH_CONTRACT.md#14-open-14-automatic-certification-within-an-approved-envelope) (D084): deterministic conformance of an exact composition of certified primitives under unchanged units, time and missingness semantics. Unsupported meaning remains a gap or requires a separately approved extension.

`certify_composition(compiled_id)` is an authenticated operator operation. The host resolves the owned compilation's completed formalization, data-bound feature certificate, retained reference certificate, exact compiler package and compatible runtime. It reconstructs the compilation input from those dependencies. No market rows are calculated or released by certification.

The reference certificate does not itself cover the additional binding driver. The new validator checks that exact retained driver against 26 independently fixed [expectations](../tests/fixtures/composition_conformance_cases.json), with a separate [derivation](../tests/fixtures/composition_conformance_expectations.md). Complete outputs cover per-program types, units, feature closure, parameter locations, warmup/grid arithmetic and row limits. Negative cases require their specific error class/code. The fixture digest is pinned. The actual candidate is then recompiled in the same checked package and its entire digest compared with the original. This second step is replay, not an independent oracle; the fixed expectations supply the independent comparison.

Before execution, `composition-source-package/1` and `composition-input/1` retain source bytes, fixture, compiled identity, runtime and expected compilation digest. Existing bound-attempt events record start, completion, interruption and restart recovery. Fresh isolated children use the retained closure and existing time/output/reaping limits. This is not an OS sandbox. Complete registry/blob backups retain the required bytes.

The host rechecks dependencies, runtime, retained bytes and validator version before issuing `composition-certificate/1`. Success is `CONFORMANT`; calculation failure retains `CERTIFICATION_GAP`. Cancellation retains an interrupted attempt and its input. Generic source/worker writes cannot issue these records. Certificates preserve exposure and grant implementation-conformance authority only.

`composition_certificate_status(certificate_id, compiled_id=None)` checks current usability and exact optional target identity. Revocation, missing/corrupt dependencies or an incompatible runtime prevent satisfaction. Changed validator revisions produce `STALE_VALIDATOR`. Historical records remain readable. Certificates and validator packages support [technical revocation](REVOCATIONS.md); a fresh package timestamp cannot evade the same revoked file footprint.

Plan preparation accepts optional `composition_certificate_id`. It retains identity, exposure and prerequisite status before calculation, then rechecks before commitment. A changed prerequisite interrupts the attempt; completed keys return historical plans. `inspect_evaluation_plan` removes only `composition_conformance` when currently satisfied. The raw plan and original gates remain immutable. Legacy plans without a certificate keep the gate open. Future scientific freeze must check all prerequisites atomically.

Conformance does not establish natural-language equivalence, data/PIT/rights/exposure acceptance, statistical calibration, full-process error control, profitability or deployment authority. Existing outcome `REVIEW_REQUIRED`, missingness and resource gaps are unchanged. Compiler warmup checks do not approve uncertain outcome dependencies or historical publication times. The [implementation report](../docs/reviews/implementation-2026-10-25/COMPOSITION_INTEGRATION_2026-10-26.md) records verification and limits.
